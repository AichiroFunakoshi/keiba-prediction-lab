# ローカルUI設計方針

## 完成形

完成形は、Mac内でPython予測エンジンを動かし、ローカルのWeb画面から操作するmacOSアプリとする。純粋なPWAやクラウドサービスにはしない。初期はローカルWeb UIとして検証し、操作手順が固まった後に`.app`として包装する。

```text
macOSアプリ／ローカルブラウザ画面
              ↓ 型付きローカルAPI
既存のPython監査・学習・予測・評価エンジン
              ↓
利用者が管理するMac内の非公開ファイル
```

## 設計原則

- 既存のPython公開APIを唯一の計算経路とし、UIに予測ロジックを複製しない
- 初期状態では外部サーバー、クラウドDB、利用状況送信を必要としない
- ファイル選択は利用者の明示操作とし、指定外ディレクトリを走査しない
- 保存前監査を通過しない予測は正式固定できない
- 既存のモデル、予測、評価成果物を上書きしない
- エラーを成功表示へ変換せず、どの入力契約に反したかを示す
- UI表示用の要約も、監査済みの型付きオブジェクトから生成する
- 実購入候補と研究用影予測を色、位置、文言の全てで区別する
- WIN5は購入額0円の影予測としてのみ表示し、対象5レースと独立仮定を明示する

## 画面構成

### ダッシュボード

- 使用中モデル版と学習終了時刻
- 学習・評価レース数
- 最新ウォークフォワード監査結果
- 未評価の固定予測数
- データ源の承認状態
- `実購入候補は三連単1点100円`という固定ポリシー

### データ管理

- 学習CSV、対象CSV、履歴CSV、脚質、想定ペースの選択
- ファイル名、SHA-256、行数、観測時刻範囲
- 欠損、重複、未知列、結果情報混入の監査結果
- データ利用権を利用者が確認した記録

UIが外部サイトからデータを無断取得する機能は置かない。将来、承認済みデータ源を追加する場合も、取得器と共通形式への変換を分離する。

### モデル検証

- ウォークフォワード窓の入力と事前確認
- 条件付きロジットと一様確率の対応比較
- 1着的中率、Brier score、Log loss、ECE
- 窓別、競馬場、距離帯、頭数、信頼度別診断
- 300レース、500レースの到達状況

評価結果から窓や係数を自動変更しない。モデル採用は別の明示操作と版変更を必要とする。

### レース予測

操作順を固定する。

1. 入力ファイルを選択
2. 発走・観測・固定時刻を確認
3. 読み取り専用監査
4. 1着確率順位と三連単候補をプレビュー
5. 新しい出力先へ正式固定
6. 保存済みバンドルを再監査

正式表示の中心は三連単1点100円とする。影予測は別パネルに置き、全行へ`購入しない・0円`を表示する。

WIN5対象日には、事前固定・監査済みのWIN5成果物を任意に追加表示する。各対象レースの1着確率1位を1頭ずつ示し、組合せ全体の確率は5レース間の独立仮定に基づく研究用参考値として表示する。WIN5の購入操作や購入額は設けない。

### 結果入力・事後評価

- 発走前予測を読み取り専用で表示
- 着順、払戻、事前レース条件を別ファイルとして追加
- 1着、三連単1点、3・5・10点での追加救済を分離
- 別1着候補による救済と買い目水増しを表示
- 最大払戻除外後の回収率と払戻集中度を表示

### 設定・監査履歴

- ローカル作業ディレクトリ
- 現在の研究ポリシー版
- 成果物スキーマ版
- 入力と成果物の監査履歴
- アプリとPythonエンジンの版

認証情報をUI設定へ保存する機能は、承認済みデータ源が具体化するまで作らない。

## ローカルAPI境界

UIはCLIの表示文字列を解析しない。次のPython公開APIを呼び、成功時は型付き値、失敗時は契約違反を受け取る。

- 入力ひな型生成
- CSV・レース入力監査
- モデル学習とモデル成果物読込
- ウォークフォワード実行・成果物読込・監査
- 1レース予測と予測バンドル監査
- 予測Markdown生成
- 払戻決済、集計、比較、ブートストラップ、条件別診断

HTTP形式のローカルAPIを追加する場合も、ハンドラーはこの層を薄く呼ぶだけにする。HTTPハンドラー内に確率計算やファイル形式検証を再実装しない。

## セキュリティ境界

- 待受先は初期状態でループバックアドレスだけに限定する
- LANやインターネットへ公開しない
- 任意パスの削除、既存成果物の上書き、シェル文字列実行をUIへ提供しない
- ブラウザへファイル内容全体を必要以上に返さない
- エラー画面へCookie、キー、原データ行を表示しない
- 外部リンクはデータ送信を伴わない通常リンクとして分離する

## 実装段階

### UI-0：型付きアプリケーション境界

既存成果物を全て再読込・監査できる公開APIを整える。現在、予測バンドルとウォークフォワード成果物は対応済みである。UIはまだ追加しない。

### UI-1：読み取り専用プロトタイプ

ローカルで既存の予測バンドルとウォークフォワード成果物を選び、監査結果と人間向けレポートを表示する。学習・予測・保存操作は行わない。

第一段階として、両成果物を監査し、画面表示用の型付き`ReadOnlyAppSnapshot`へ変換する境界と`inspect-app-state` CLIを実装済みである。実購入候補、影予測、勝率順位、ウォークフォワード全体指標を別フィールドで返し、入力ファイルは変更しない。

第二段階として、同じスナップショットを配信する`serve-read-only-api`を実装済みである。待受先はIPv4ループバック`127.0.0.1`だけに固定し、Hostヘッダーを検査し、書込み系HTTPメソッドを拒否する。レスポンスはキャッシュ禁止とし、元ファイルのパスや内容全体を公開しない。

第三段階として、同一オリジンの読み取り専用画面を実装済みである。正式候補の三連単1点100円を最上段、1着候補と確率順位を中央、影予測0円をその下、任意のWIN5影予測とウォークフォワード指標を下段に置く。画面が持つ唯一の操作は監査済みスナップショットの再読込であり、入力選択、再計算、保存、投票は行わない。成果物に存在しない馬名、競馬場名、距離、馬場、評価理由は画面側で補完しない。

### UI-2：監査付き実行

入力選択、事前監査、ウォークフォワード実行、1レース予測を追加する。保存ボタンは監査成功後のみ有効にする。

### UI-3：事後評価ダッシュボード

結果・払戻の別保存と、期間・券種・条件別の診断を追加する。少数標本警告を常時表示する。

### UI-4：macOSアプリ包装

操作フローとローカルAPIが安定した後に`.app`化する。包装技術はこの段階で、保守状況、署名・配布、Python同梱方法を比較して決定する。

## UI着手前の完了条件

- UIが必要とする保存済み成果物に監査ローダーがある
- 正常・改変・欠落・型不正の合成fixtureがある
- UI向けAPIがファイルを上書きしない
- 実購入と影予測を区別する値が型として取得できる
- ローカルだけで全テストを実行できる

最初のUI実装はUI-1に限定する。見栄えより、監査済み情報だけを誤解なく表示できることを優先する。
